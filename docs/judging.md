# Judging design

Some of what you actually care about cannot be counted. Whether an abstraction earns its place,
whether a comment carries intent or just restates the line below it, whether the code reads like
something you would want to maintain — a node count says nothing about any of it, and a model can
score well on one while writing something unreadable.

So the `design` dimension is judged by a reviewer model. This document is about the one hard
question that creates: **what makes a judged verdict true rather than merely stated?**

## Where the line sits

| Judged | Counted |
|---|---|
| Does this abstraction earn its place | Node count, nesting depth, file count |
| Is a comment recording intent, or restating the code | Does it parse, stdlib only, no `eval` |
| Would you want to maintain this | Behaviour across the hidden case grid |

If something is countable, it is counted. The reviewer only gets what genuinely needs reading.

## Five rules

**1. Correctness gates the reviewer.** Only submissions that pass every correctness check are
reviewed. Otherwise you are scoring the elegance of a wrong answer, and paying quota to do it. A
submission that fails first carries a note saying so, and no design score.

**2. Design never touches correctness.** It is its own dimension, its own column, excluded from
the headline. A formatting miss is not a wrong answer, and neither is an unearned wrapper.

**3. Binary questions, not scores.** Never "rate this 1–10" — that number means something
different on every invocation and every model. Each task declares a fixed set of yes/no questions
in its private grader, phrased so that *yes* means a defect is present.

**4. Every defect must cite a line that exists.** Evidence is `path:line | the source line,
copied exactly`. The citation is then checked mechanically against the submission. A defect whose
citation cannot be found is the reviewer's own hallucination and is discarded — scored as clean,
with the discard kept visible in the evidence. This is the single most important mechanism here:
it makes inventing work cost the candidate nothing.

**5. The reference is the scale anchor.** "Simple enough" is meaningless without something to be
relative to, so the known right-sized reference solution goes in the reviewer's prompt. Different
names, ordering or formatting from the anchor are explicitly not defects.

## The rubric

The reviewer's instructions are derived from the recorded standard in
`~/.claude/skills/ruthless-code-review` and `code-simplify`, condensed to what a reviewer can act
on: smallest clear behaviour-preserving implementation; delete what is unnecessary; remove
abstractions that are not earned; **fewer lines is not the goal, faster comprehension is**;
removing error handling to look cleaner is a defect, not a simplification; no speculative
improvements and no harmless nits.

Submissions are untrusted data. Text inside one is never an instruction to the reviewer.

## Keeping every model on one scale

Five biases would otherwise wreck cross-model comparison.

**Self-preference.** A reviewer tends to go easy on its own family. The default reviewer is
deliberately not an Anthropic model, because the Claude Code candidates would otherwise be graded
by relatives. The Settings tab warns when you pick a same-family reviewer. And rather than quoting
an effect size from a paper, you can measure it here:

> A reviewer can be a Pi-catalog model (reached over the API adapter) **or** a Claude Code model
> (the first-party CLI under your own plan login, with every tool denied and one turn). The second
> exists because a plan login is sometimes the only working credential. It is the same client the
> Claude Code candidates use, so if you review Claude submissions with it, run the probe below —
> that is exactly the case self-preference describes. The reviewer's provider is part of the
> comparison key either way.

```sh
npm run test:judge -- --run <runId> --alt <provider>/<model>
```

That reviews the same real submissions with two reviewers from different families and prints the
defect rate split by the family that wrote the code. A reviewer soft on its own relatives shows a
wider gap on that row than on the others.

**Length bias.** Judges reward longer answers, which would invert the thing being measured. Length
is never a judge question, the rubric says so explicitly, and the calibration set contains a
longer-but-clean case as a trap.

**Style fingerprints.** Authorship signals — model and vendor names, "generated by", AI
self-references — are stripped before review, and the reviewer is never told who wrote what.
Comments are deliberately *not* stripped: unnecessary comments are one of the things being judged,
so removing them would delete the evidence. Writing style remains a residual leak, which is why
self-preference is measured rather than assumed away.

**Position bias.** Avoided by construction: submissions are reviewed one at a time against a fixed
anchor, never against each other.

**Instability.** Set rounds above 1 and each submission is reviewed N times and settled by
majority; a tie counts as no defect. The evidence line records how many rounds agreed, so an
unstable verdict is visible rather than laundered into a number.

**The reviewer is part of the experiment.** Its provider, model, thinking level, round count and
the rubric text all enter the comparison key. Change any of them and older runs will not pool with
the new ones — the same discipline already applied to the suite, harness, lane and cache.

## Calibrating against your own standard

A judge you cannot validate is an opinion. A judge with a measured agreement rate is an instrument
with a known error bar.

`suites/personal/private/calibration/` holds labelled submissions. Every one is behaviourally
correct — correctness gates the reviewer, so a broken case would calibrate on code that would
never reach a reviewer. Every label carries a `why` naming the recorded rule it comes from: a line
in the written standard, or a complaint that recurs across the transcripts.

Three of the eight cases contain no defect at all, and two of those are traps:

- `longer-but-plain` — longer than the anchor, no defect. Catches length bias.
- `why-comment-kept` — carries a comment explaining *why*, plus a restructured expression. Catches
  a reviewer that treats any comment, or any unfamiliar shape, as noise.

`npm run test:suite` checks the whole set offline, with no model calls: every case is fully
labelled, labelled only for questions that exist, and behaviourally correct. So `npm run
test:judge` adds exactly one thing — the reviewer's opinion:

```
Agreement with the recorded standard: 32/32 (100%)
  invented defects (reviewer saw one that is not there): 0
  missed defects:                                        0
  clean cases in the set: 3/8
```

Invented and missed defects are reported separately rather than averaged, because the standard
treats inventing work as its own failure. Every disagreement also prints the check's evidence,
because "said clean" has two very different causes — the reviewer saw nothing, or it saw
something and the citation check rejected the proof. Those need to be told apart.

**Read a perfect score as "no disagreement found yet", not as "this reviewer is right".** Eight
cases and thirty-two judgments is a small set. It earns its value by growing.

Measured so far: `claude-code/sonnet` and `claude-code/haiku` both 32/32 at one round. That does
not separate them, so this set cannot yet be used to *choose* a reviewer — only to show that
neither contradicts the standard on these cases. An earlier Haiku round also reported a defect
that a later round did not, which the citation fix does not explain: single-round judging is
unstable. Prefer 3 rounds over 1, and read the agreement count in each check's evidence.

Compare reviewers without touching your saved settings:

```sh
npm run test:judge -- --judge <provider>/<model>
```

## Growing the set

When the reviewer and you disagree on real code, that disagreement is the informative case. Add it
to the calibration file with your verdict and the reason, and the set grows exactly where it
matters. Same principle already in this suite: a rule that capable models consistently flag is an
ambiguous rule, not a model error.

## What this costs

Three honest losses, worth knowing before you switch it on:

1. **Reproducibility.** Every other number here replays exactly from the saved artifacts. Design
   does not. That is why it is quarantined in its own dimension and labelled as judged everywhere
   it appears.
2. **Quota.** One reviewer call per reviewable trial per round. Off by default; turning it on is a
   billing decision and goes through the same consent path as a metered candidate.
3. **A new surface.** The reviewer reads model output. It is prompted to treat submissions as
   data, runs with no tools and cannot take a follow-up turn, but the risk is not zero.

A reviewer that cannot run — expired login, usage limit, unparseable reply — produces no design
checks and a note on the trial. It never fails a candidate. Harness problems must never look like
model problems; that is the whole point of the framework.

## Adding a judged task

1. Declare `design` in the task's `dimensions`.
2. Export a `review` from the private grader:

```js
export const review = {
  anchor: {'module.py': REFERENCE_SOURCE},   // must equal the reference solution
  paths: ['module.py'],                      // only these files reach the reviewer
  items: [{id: 'rule-duplicated', ask: 'Is the decision still spelled out in more than one place…'}],
};
```

3. Add labelled cases to `calibration/<task>.mjs`, including at least one with no defect.

`npm run test:suite` enforces the structure: the anchor must be the reference solution, questions
must be specific, graders must never emit `design` themselves, and a review rubric without the
`design` dimension (or the reverse) is an error.
